# Taste
- For Flutter state management, prefers Riverpod over Provider. Confidence: 0.85
- Targets Flutter 3.x / Dart 3.x with Material 3 as the baseline. Confidence: 0.7
- Prefers feature-based Clean Architecture for Flutter apps — layering `core/`, `models/`, `services/`, `providers/`, and per-domain `features/` folders with dedicated config/constants/theme/routes/widgets/utils subfolders. Confidence: 0.75
- Wants production-grade deliverables: explicitly rejects prototypes, demos, or static UI mockups in favor of complete, scalable, functional apps with real auth, data layers, error handling, loading/empty states, and validation. Confidence: 0.8
- Expects the finished project to run immediately out of the box (`flutter pub get` then `flutter run`) without manual setup steps, degrading gracefully when external services (e.g. Firebase) aren't configured. Confidence: 0.7
- Works iteratively across sessions on the same codebase and expects the agent to pick up where it left off — inspect the current code state before continuing rather than restarting. Confidence: 0.55
- For auth flows, wants registration to create the account and then return the user to the login screen to sign in explicitly, rather than auto-signing them in and going straight to home. Confidence: 0.6
- Expects form validation to work correctly (name, password, confirm-password, etc.) and auth/data failures to surface a clear, user-facing explanation instead of a generic "failed" message. Confidence: 0.6
- Wants person-name input fields to accept letters only (rejecting digits and stray symbols like "123" or "Ali@") while still allowing real-name separators such as spaces, hyphens, apostrophes, and dots. Confidence: 0.6
- Wants authentication to be complete and hardened rather than minimal: enforced email verification, Google sign-in/sign-up, forgot-password reset, strict login/sign-up field and password validation, and optional profile-photo (avatar) selection via camera or gallery right on the sign-up form with instant local preview. Confidence: 0.6
- Communicates in Roman Urdu (Urdu written in Latin script) and expects replies in Roman Urdu, including end-of-task summaries. Confidence: 0.6
- Expects code changes to be verified before being reported done — `flutter analyze` clean and the full `flutter test` suite passing — and new features to ship with accompanying tests. Confidence: 0.55
- Reports bugs and issues by sharing screenshots with little or no accompanying text, expecting the agent to read the image and diagnose the root cause on its own. Confidence: 0.8
- Wants long user-entered text (descriptions, goal titles, category labels, names) to wrap or ellipsize gracefully instead of overflowing (no RenderFlex overflow), and expects this handling applied consistently across every screen and category. Confidence: 0.6
- Expects image/media features to actually work end-to-end: a picked photo should be shown to the user immediately (from local bytes) rather than waiting on the network, async operations like uploads must not leave the UI stuck in an indefinite loading state, and failures should surface the real cause instead of appearing silently broken. Confidence: 0.55
- Prefers removing code and dependencies that are no longer needed rather than leaving them in place: when a feature or library becomes redundant (e.g. after swapping out Firebase Storage), expects the old service files, providers, dependency entries, and related docs to be deleted, not parked. Confidence: 0.6
- Willing to bring in third-party cloud services for functionality Firebase handles awkwardly — e.g. prefers Cloudinary (CORS-enabled unsigned uploads over REST) over Firebase Storage for image uploads. Confidence: 0.5
